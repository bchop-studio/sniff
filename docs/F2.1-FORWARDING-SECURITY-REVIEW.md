# F2.1 forwarding proxy security review

**Review date:** 2026-08-10

**Reviewed snapshot:** `1e8e4eea7face1974bd3bbb59004152de75f95bb`

**Release claim under review:** a local alpha that scans agent messages and forwards approved requests to an upstream HTTP service.

## Verdict

**NO-GO for a general-purpose or transparent forwarding proxy.**

**CONDITIONAL GO for one narrow local-alpha slice:** a loopback-only, authenticated gateway that accepts one normalized JSON message schema and can forward only `CLEAN` requests to one exact, process-configured HTTPS upstream. It must not accept a destination URL, upstream credential, arbitrary headers, redirects, streaming, WebSockets, `CONNECT`, or raw proxy traffic from the caller.

The existing screening gateway remains safe to describe as an authenticated, bounded, non-forwarding local alpha. This review does not find a reason to remove that claim.

## What is already proven

The current gateway:

- rejects non-loopback binds in `src/sniff/gateway/server.py:76`;
- requires a bearer token and compares fixed-length SHA-256 digests with `hmac.compare_digest` in `src/sniff/gateway/server.py:31`;
- bounds request bytes, message count, message content, socket time, and concurrent requests in `src/sniff/gateway/server.py:22`;
- treats every submitted role as untrusted before scanning in `src/sniff/gateway/server.py:140`;
- returns finding metadata without source excerpts and suppresses request logging in `src/sniff/gateway/server.py:147` and `src/sniff/gateway/server.py:206`;
- contains no outbound client in the gateway package.

Fresh evidence on the reviewed snapshot:

- `uv run ruff check src tests` passed.
- `uv run pytest -q` passed, 134 tests collected.
- `uv run pytest tests/test_gateway.py -q` passed, 19 tests.
- `uv run pytest tests/test_url_fetch.py -q` passed, 36 tests.

These checks prove the current screening service. They do not prove forwarding safety.

## Blocking risks

### 1. Caller-controlled destinations turn the gateway into SSRF

A destination URL supplied in the request could reach loopback services, private networks, cloud metadata, alternate URL schemes, unsafe ports, or a public host that later resolves or redirects internally.

**Required design:** the first slice has one exact upstream origin configured when the process starts. The request body cannot override its scheme, host, port, or base path. Use HTTPS only, the default port only, and an explicit endpoint-path allowlist. Disable redirects. Normalize the configured origin once and reject userinfo, fragments, control characters, IPv6 zone identifiers, alternate numeric-IP spellings, malformed authorities, trailing-dot ambiguity, and Unicode or IDNA lookalikes.

The URL-mode guard in `src/sniff/cli/url_fetch.py` is useful reference logic, but its global `socket.getaddrinfo` swap is explicitly unsuitable for a multithreaded server at `src/sniff/cli/url_fetch.py:261`. It must not be reused as the forwarding transport. The server transport must validate every DNS answer at connection time, connect only to the validated public address, and preserve the configured hostname for TLS certificate and SNI checks.

### 2. The gateway token conflicts with upstream authorization

The current endpoint consumes `Authorization` as the gateway credential. A transparent proxy would also need that header for the upstream API. Blind forwarding could leak the gateway token; accepting a caller-provided upstream token would expose secrets to logs, errors, or the wrong destination.

**Required design:** use a separate gateway-auth header and strip it before egress. Load the upstream credential from process configuration, map it only to the fixed upstream, and inject it after destination validation. Never accept credentials in a URL or JSON body. Never return or log either credential.

### 3. Raw header forwarding enables credential leaks and parser attacks

Hop-by-hop headers, spoofed forwarding headers, duplicate framing headers, and `Connection`-nominated headers can cause request smuggling or change how the upstream parses the request.

**Required design:** use an allowlist, not a copy-and-strip denylist. Rebuild the outbound request from parsed values. Set `Host`, `Content-Length`, upstream authorization, and `Accept-Encoding: identity` inside the gateway. Reject duplicate or comma-separated `Content-Length`, any `Transfer-Encoding`, premature EOF, obsolete folded headers, control characters, `Connection`, `TE`, `Trailer`, `Upgrade`, `Proxy-Authorization`, `Proxy-Authenticate`, `Forwarded`, `X-Forwarded-*`, cookies, and caller-supplied `Host`. Do not reuse inbound connections for the first slice.

### 4. Scan bypasses exist if the proxy accepts arbitrary JSON

The scanner currently understands message text, including text parts in a content list. A general model API can place instructions in other fields, nested objects, tool outputs, files, images, encoded data, or provider-specific shapes. An empty or unrecognized message can be counted as skipped and appear clean. Current content-size accounting also ignores unsupported fields and parts, and a payload split across adjacent messages can evade a rule that scans each message alone.

**Required design:** support one versioned request schema. Reject duplicate security-relevant JSON keys, unknown top-level fields, unknown message fields, non-text content, encoded payloads, attachments, and any request where a message is skipped or zero messages are scanned. Scan every supported field individually and scan the canonical aggregate across message and content-part boundaries. The exact normalized values scanned must be the values serialized upstream. Do not forward merely because the rolled-up verdict is not `DANGEROUS`.

For the local-alpha slice, only a `CLEAN` verdict may forward. `SUSPICIOUS`, `DANGEROUS`, scanner exceptions, scanner timeouts, malformed input, and unsupported input all fail closed with no upstream connection.

### 5. A check-then-forward race can send blocked data

Tests that assert only the returned status do not prove that rejected content was never sent. A forwarding bug could open the connection or write part of the body before scanning finishes.

**Required design:** parse, validate, and scan the complete bounded request before resolving, connecting to, or writing to the upstream. The outbound transport must sit behind a narrow seam that tests can replace with a recorder. Every failure-path test must assert zero resolver calls, zero connection attempts, and zero outbound bytes.

### 6. Upstream responses create a second untrusted boundary

A valid upstream can return oversized, compressed, malformed, redirected, or prompt-injected content. Passing it straight back gives an agent unreviewed inbound instructions.

**Required design:** disable redirects and automatic decompression, request identity encoding, enforce connect/read/total timeouts, cap response headers and body bytes, require the expected status and JSON content type, parse one supported response schema, scan every returned message as untrusted, and return only a bounded normalized response. A blocked or malformed response fails closed and does not expose its body in the error.

Streaming and Server-Sent Events are cut from this slice because sniff cannot safely approve a message before the full message exists.

### 7. Localhost is not an authentication boundary

Other local processes can reach loopback. A browser can also target localhost, and a minimum character count does not guarantee token entropy.

**Required design:** require a randomly generated token with at least 256 bits of entropy, reject `Origin` requests, send no CORS allow headers, rate-limit authentication attempts before reporting validity, and return the same bounded error shape for missing and wrong credentials. Keep loopback binding enforced in the server class, not only in the CLI.

### 8. Forwarding multiplies denial-of-service paths

Request concurrency is currently bounded, but forwarding adds DNS, connection pools, slow upstreams, response bodies, decompression, retries, and scanner work.

**Required design:** use one total deadline, strict DNS/connect/TLS/read timeouts, bounded request and response headers, bounded wire and decoded bodies, a bounded worker pool, and no automatic retries. Reject excess work with a complete JSON response rather than silently dropping the socket. Hold a concurrency slot until the upstream response is fully closed. Key any connection pool by the fully validated origin, DNS policy, and TLS identity so a connection can never cross those boundaries.

### 9. Error and audit behavior can leak private data

Network exceptions often contain full URLs, headers, response fragments, or resolved addresses. Raw request or response logging would preserve prompts and credentials.

**Required design:** return stable error codes, not raw exception text. Security logs may contain time, outcome, rule IDs, destination ID, byte counts, and a one-way request correlation ID. They must not contain credentials, URLs with query strings, headers, request bodies, response bodies, finding excerpts, or source text.

## P0 must-pass test matrix

No forwarding code is ready for review until automated tests prove all of these properties.

### Destination and transport

1. A request cannot set or override scheme, host, port, base path, DNS resolver, or proxy environment settings; parser-confusing userinfo, fragments, zone IDs, numeric forms, trailing dots, and Unicode or IDNA lookalikes are rejected.
2. Loopback, private, link-local, multicast, reserved, unspecified, CGNAT, IPv4-mapped IPv6, malformed, and mixed public/private DNS answers are blocked.
3. A public preflight answer followed by a private connection-time answer is blocked with zero connection.
4. Redirect status codes are returned as a safe gateway error and are never followed.
5. TLS certificate and hostname failures are fatal; no insecure mode exists.
6. Ambient `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` variables cannot reroute egress.

### Authentication and headers

7. Missing, wrong, short, oversized, and malformed gateway credentials use the same rate-limited path and never reach the upstream.
8. The gateway credential is absent from the outbound request.
9. The configured upstream credential is sent only to the exact configured origin and is absent from responses and logs.
10. Duplicate equal or unequal and comma-separated `Content-Length`, `Content-Length` plus any `Transfer-Encoding`, malformed chunks, trailers, premature EOF, obsolete folded headers, control characters, hop-by-hop headers, `Connection`-named headers, caller `Host`, cookies, and spoofed forwarding headers are rejected.
11. The outbound request has one gateway-generated `Host` and `Content-Length` and uses `Accept-Encoding: identity`.

### Parse, scan, and forward order

12. Invalid or deeply nested JSON, duplicate security-relevant keys, extra fields, unsupported roles, non-text parts, attachments, empty messages, skipped messages, and over-limit input make zero resolver, connection, and write calls.
13. `SUSPICIOUS` and `DANGEROUS` inputs make zero resolver, connection, and write calls.
14. Scanner exceptions and timeouts make zero resolver, connection, and write calls.
15. Only a fully parsed and fully scanned `CLEAN` body reaches the transport. Tests prove the normalized values scanned are exactly those serialized upstream, including an aggregate scan that catches injection split across adjacent messages or text parts.
16. Concurrent blocked and clean requests cannot share state, credentials, bodies, or verdicts.

### Response boundary

17. Oversized headers or bodies, compression, wrong content type, malformed JSON, unsupported fields, redirects, timeout, disconnect, and TLS failure all return bounded safe errors.
18. Upstream response text is scanned before any response bytes reach the client.
19. `SUSPICIOUS`, `DANGEROUS`, skipped, malformed, and over-limit upstream messages are not returned to the client.
20. Upstream credentials, raw exception text, upstream body fragments, and prompt excerpts never appear in client errors or logs.

### Resource and lifecycle behavior

21. The concurrency limit returns a stable overload response and never silently closes the connection.
22. Slow headers, slow bodies, stalled DNS, stalled connect, and stalled response reads all terminate within the total deadline and release their slot.
23. Client disconnects close the upstream response and release all resources.
24. No retry occurs after a partial or failed upstream write.
25. Shutdown stops accepting work, closes active upstream connections, and does not leave worker threads running.
26. A pooled connection validated for one hostname, port, DNS result, destination policy, or TLS identity cannot be reused for another.

## Mandatory scope cut for the next slice

**Keep:** loopback bind, gateway authentication, one normalized JSON schema, one fixed HTTPS upstream, server-injected upstream credential, full buffering, `CLEAN`-only forwarding, bounded normalized JSON responses, and fail-closed behavior.

**Cut:** arbitrary destinations, transparent HTTP proxying, `CONNECT`, redirects, streaming, Server-Sent Events, WebSockets, multipart uploads, files, images, arbitrary headers, cookies, compression, retries, multiple providers, and private-network upstreams.

**Do not claim:** production ready, general proxy, complete prompt-injection protection, transparent drop-in compatibility, or protection against every encoded or multimodal payload.

## Approval boundary

This document approves design work and tests for the narrow slice only. It does not approve outbound network code. The first implementation pull request must stop for BChop's review after the tests and transport seam are written, before live forwarding is enabled.
